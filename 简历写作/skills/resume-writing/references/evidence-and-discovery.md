# 经历、证据与补问

## 最小可用素材

材料足够写初稿就先写，不要求填完整表格。需要长期维护时，可在用户的求职项目内按以下字段整理：

| 字段 | 记录内容 |
| --- | --- |
| 经历身份 | 工作、实习、个人项目、课程、小组实践、公益等 |
| 时间与角色 | 公司或项目、起止时间、正式职位、本人负责范围 |
| 问题与约束 | 为谁解决什么问题，已有方案、资源、成本或交付限制 |
| 本人行动 | 具体动作、决策、交付物、协作对象与分工 |
| 结果与阶段 | 已交付什么、谁使用、验证方式、当前完成到哪里 |
| 指标口径 | 数据来源、时间、单位、基线、样本、计算方法 |
| 来源与确认 | 用户原话、文档、演示、记录、公开链接，以及未确认之处 |
| 可用表述 | 用户已确认的措辞、披露限制、不能使用的说法 |

素材库可以只包括经历条目、成果素材、待补证据和已确认表述，无需固定十九节。用户暂不提供联系方式、照片、年龄、婚育、签证等信息时，不为完整性强求；只在目标岗位和用户意图确有需要时处理。

## 只补会改变简历的问题

优先从现有材料回答，再选择最有价值的缺口追问：

- 你本人具体负责哪一段？哪项决定是你提出或拍板的？
- 实际交付了什么，目前到哪一步？谁使用过，怎样验证？
- 有可追溯的前后变化吗？没有业务指标时，有哪些明确交付或验收记录？

按岗位改变追问重心：产品看需求、取舍和验证；工程看实现、约束与可靠性；设计看使用场景、方案迭代与交付；运营销售看执行机制、归因与实际结果；其他行业沿用其业务语言。

不能把建议的问题清单写成候选人已经做过的经历。用户说暂不补材料时，用现有证据完成，并把需要补的内容控制在少数关键项。

## 技能掌握与技术栈分开核实

分别核实使用情境、完成方式和本人能做的事：课程或简单练习、个人项目或商业工作；AI 辅助还是独立完成；能否解释、操作、修改或调试。项目采用某框架、依赖中出现某技术，不足以证明候选人熟练掌握。

只补问会改变声明的问题，例如“代码主要由谁编写，自己能读、改、运行或排错到什么程度”。已有回答直接沿用，不重复问；信息不足时用有依据的行为表述，不默认写熟练，也不把所有能力一律降为了解。

技能标签按材料选择，可以区分常用工具、项目使用、AI 辅助开发、基础了解和课程实践，不必强排为一套熟练度等级。工具后尽量对应能完成的任务。使用 AI 交付作品可以体现需求、设计、集成与验证能力；“能运行并配合排错”不能扩大为独立开发或独立调试。

## 冲突与贡献归属

材料冲突时不要自动选择更新或更好看的版本。优先核对当事人明确陈述和可追溯记录；仍不能判断时保留待确认状态，避开争议细节起稿。新文档可能写的是规划，旧记录也可能已过时。

团队项目至少分清三个层面：团队整体成果、本人承担工作、本人能够支持的影响。团队人数不是管理人数；协作不是全面负责；给过建议不是主导；做出工具不是被用户采用。

按关键功能核对阶段和版本归属，尤其是一个项目同时存在已发布能力、当前代码迭代和未来方案时。代码与测试文件存在只支持相应实现记录，不能直接推断当次测试已运行、真实服务效果已验收，或最新功能已进入发布包。用户说“主要自己测试”时保留这个限定，不擅自推成绝无其他试用者或已有用户验证。

“已确认表述”用于保护候选人的真实语义和披露边界，不是豁免事实核验。若新证据与旧表述冲突，应指出冲突后修正，而非机械沿用。

### 有限证据怎么写

| 原始材料 | 可以写的方向 | 不能补写 |
| --- | --- | --- |
| 做出课程演示，未正式上线 | 完成课程项目演示；有原型或验证记录时再据实写明 | 仅凭演示就写原型验证、商业上线、服务企业客户 |
| 与其他团队共同完成 | 说明本人负责环节与协作结果 | 负责全部系统或管理整个团队 |
| 只有若干测试记录 | 具体测试范围、当次验收状态 | 真实业务质量、生产稳定性提升 |
| 缺少效果数据 | 写实际交付、覆盖任务、设计取舍 | 推算效率、假设增长、显著改善 |
| 工具由 AI 辅助生成 | 写需求判断、设计、集成与检查 | 无依据的独立手写或自研底层技术 |

这些是写法示例，不是任何候选人的真实经历。
