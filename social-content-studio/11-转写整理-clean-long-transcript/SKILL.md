# 长转写稿洗稿（ASR 转写 → 书面稿）

## 适用场景

输入是几百到上千段的录音 / 字幕 ASR 转写稿，口语化严重、充满口水词、夹杂 ASR 错字。目标是产出通顺的书面稿，信息不丢、段落不改。

## 核心原则

1. **洗稿 ≠ 改写**。只做三件事：删口水词、理顺碎句、修 100% 确定的错字。不扩写、不加解释、不改变原意、不丢事实。
2. **一段对一段**。输入多少段，输出就多少段，顺序不变。不合并、不拆分、不新增、不删除。
3. **专有名词保守**。人名、模型名、产品名、公司名、数字，没有十足把握就原样保留，绝不臆造。宁可留个可疑词，也不要写错——写错比留着更糟。
4. **读不通的片段**：ASR 纯乱码且无信息量可以删；只要有信息量，就得想办法理顺保留。

## 三种交付形态（先分清再动手）

同一个 ASR 稿，用户可能要三种不同的东西。**形态搞错，活儿全白干。**

| 形态 | 特征 | 什么时候用 |
|---|---|---|
| **① 洗稿版**（默认） | 一段对一段，段号与原稿一一对应；只删口水、理顺碎句、修确定的错字 | 常规需求；后续要做段级对照、术语待核清单、汇总，都依赖它 |
| **② 知识点 / 汇总** | 按主题重排，只取概念、结论、金句，标注段号出处 | 用户问"XX 讲了什么""整理成笔记" |
| **③ 整理稿** | **丢废话、保论证链**：删掉现场杂音与无关段落，但**老师铺垫的论证过程必须留** | 用户明确说"去掉废话只留重点""不要只留金句" |

**形态 ③ 的判据只有一条，但它反直觉**：用户要的"重点"包括**铺垫**——举例、递进、自我纠正、甚至跑题的类比。只摘结论句会被打回。实测用户的原话是"重点内容不要只留金句，老师铺垫的那些文字也都要留"。

### 形态 ③ 的变体：**去杂音**（在洗稿版之上再删整段废话）

用户可能接着提"没用的废话也删掉，比如课间休息时录进去的"。

**默认就地改在洗稿版里，不要另建一个"去杂音版"文件。** 用户明确纠正过一次原话是"把课间的杂音去掉，放在洗稿版里面，不用单独再列一个去杂音版"——**他不喜欢同一份内容产出多个近似文件**。真拿不准就先问，别自作主张拆成两份。

**代价与必做的补救**：原地删会让段号**不再与原稿一一对应**，而待核清单 / 汇总 / 前言里的段号全靠它。所以必须同步做两件事：
1. 在**配套清单顶部写明**"段号 = 现行稿段号，已删去课间杂音 N 段，被删区间为 …（按删前编号）"；
2. 把清单里**所有段号按新编号重算**（`新号 = 旧号 − 删前 ≤ 旧号的段数`），并跑一遍机器校验。
   实测一次删掉 131 段，30 多个引用段号全部要重算——**漏掉这一步，整份清单的段号就全废了**。

**删除标准（一条就够）**：**整段都是闲聊 / 调试杂音 / 无意义碎片才删；只要夹着讲课信息，一律保留。** 宁可少删，不要错删——把讲课内容删掉比留着杂音糟得多。

**定位删除区间的高效方法**（别逐段通读全稿）：
1. `grep` 休息/上下课标记定位时段边界：`下课|休息|上厕所|我们继续|下播|上课`；
2. 再看**每个边界前后各 2-3 段**，确认上下文能接上（接缝抽查）；
3. 散落的纯碎片段（`≤ 12 字 && 无拉丁字母 && 无技术词`）用脚本列出后人工过一遍。
实测 811 段的稿子，这样只花几次检索就定出了 5 个杂音时段（共删 131 段），比通读全稿快得多，也没误删夹带内容的段。

**注意课间也可能夹带有用信息**（实测：课间聊浏览器的一段讲了 ARC / DIA / 侧边栏一键折叠）。删完要**把这几个"边界段"单独列给用户**，说明可随时捞回。

形态 ③ 的两个做法：
- **现场点评类内容按问题类型归并**，不要逐条流水账。实测一次 30 多个作品的点评，归并成 12 类通用问题（阅读体验 / 一致性 / 控件不要做重 / 别互相遮挡 / 用真实素材 / "介绍产品≠做产品" / 炫酷≠元素堆砌 / 延迟是硬伤 …）比逐条保留有用得多。同时注明"要看某个对象的原始点评，回原稿对应区间"。
- **压缩比大致 7:1**（实测 34,191 → 4,975 字符）。低于 5:1 说明废话没删干净，高于 10:1 要警惕把铺垫也砍了。

## 标准流程

### 第 1 步：先摸结构，别急着读全文

```bash
wc -l -c "<文件>"
```

再用 Python 统计总行数、空行位置、段落长度分布，判断段落是怎么分隔的。常见两种：
- 每行一段（正文行与空行交替）→ 段落数 = 行数 / 2
- 空行分隔的多行段落 → 用空行切分

**⚠️ "正文行与空行交替"时，务必要确认正文落在奇数行还是偶数行——不同批次的文件会不一样。** 实测：0921-0923 那几篇段落都在**奇数行**（段号 N = 行号 2N-1），而 0924 那篇段落全在**偶数行**（段号 N = 行号 2N，第一行是空行）。**这个判据错了，后面所有 Read 的 offset 都会整体偏移一段，轻则分块错位、重则整篇串行。** 判据就一行代码：

```python
nb=[i+1 for i,l in enumerate(open(p,encoding='utf-8').read().split('\n')) if l.strip()]
print("全为奇数行:", all(n%2==1 for n in nb), " 全为偶数行:", all(n%2==0 for n in nb))
```

**必须先确认段落总数，它是后面所有校验的基准。**

### 第 2 步：按空行边界切块

不要按固定行数硬切，否则会切断段落。用空行位置对齐边界，每块 150–200 段（子 agent 单次输出上限约 8–10K token，200 段是安全上限）。

### 第 3 步：派子 agent 并行洗

每块一个子 agent，prompt 里必须写清楚：
- 文件路径 + 精确行号范围 + offset/limit
- 输入段数，以及"输出必须正好多少段"
- 完整的洗稿规则（见下方模板）
- 输出文件路径
- "如果一次写不完，先 Write 一半，再用 Edit 追加"（防止单次输出超限丢内容）
- "不要把文件内容粘贴到回复里"

洗稿规则模板（直接复制进每个子 agent 的 prompt）：

```
1. 一段对一段：输入 N 段，输出必须正好 N 段，顺序不变。不合并、不拆分、不新增、不删除。
2. 删除口语填充：啊/嗯/呃/哦/嘛/吧/呢/哈/OK/对吧/是吧/对不对/你知道吧/我跟你说；
   句首冗余衔接"好，""然后""那""所以呢""就是说"；作口头禅用的"这个""那个"；
   无意义重复与自我更正（"我我在做""这个这个""就是就是"）。
3. 破碎句子重组为通顺的书面句，允许调语序、合短句，但不得改变原意、不得新增信息、
   不得丢事实（数字/案例/人名/产品名）。
4. ASR 错字只改 100% 有把握的；没把握的专有名词、人名、模型名、数字一律原样保留，绝不臆造。
5. ASR 纯乱码且无信息量的片段可以删；只要有信息量就必须理顺保留。
6. 保留原有的第一人称口吻，不要改成第三人称或学术腔。
7. 不扩写、不加标题、不加小标题。
输出：纯文本，每段一行、段间空行；无 markdown、无序号、无 emoji；
文件内不出现任何说明、注释、总结、前言、后记。
```

### 第 4 步（关键）：校验产出，不要相信"已派发"

**子 agent 可能静默失败——不产出文件、或只写一半。必须逐块校验。**

```python
orig = [l.strip() for l in open(SRC, encoding="utf-8").read().split("\n") if l.strip()]
out  = [l.strip() for l in open(PART, encoding="utf-8").read().split("\n") if l.strip()]
print(len(orig), len(out))                                    # 段数必须相等
print(sum(len(out[i]) / max(len(orig[i]), 1) for i in range(len(out))) / len(out))
```

- **段数对不上** → 缺段或串段，该块重做。
- **平均压缩比 < 0.6** → 大面积丢内容；**> 1.0** → 在扩写，违反原则。健康区间约 0.75–0.90。
- 找出**压缩最狠的 5–10 段**，逐段人工对照原文，确认是"原文本身就是乱码"而不是"洗丢了"。
- 子 agent 挂了就自己手工洗那一块，别反复重派。

### 第 5 步：拼接 + 终检

```python
out = []
for i in range(1, N + 1):
    out += [l.strip() for l in open(f"part{i}.md", encoding="utf-8").read().split("\n") if l.strip()]
open(DST, "w", encoding="utf-8").write("\n\n".join(out) + "\n")
```

终检项：段数等于原始段数、无 emoji、无 markdown 标记（`#` / `**` / ``` / 行首 `-`）。

注意：以数字开头的段落（如 "2015年…"）会被 `^[0-9]` 规则误判成 markdown，需人工排除。

### 第 6 步：术语纠错（用户提出时做的第二轮）

ASR 稿的专有名词错误密度远超预期。去口水词那一轮按"不确定就保留"处理，必然留下一大批错字。用户要求纠错时：

1. **先向用户要标准答案**。用户往往知道（"AMI 其实就是 AI 漫剧"）。一个准确的锚点能连带解开一串同源错误。
2. **分块派 agent 做审计，只出清单、不改文件**。每块一个 agent，prompt 里给足领域背景词表，要求输出表格：`行号 | 原文片段 | 问题 | 建议修正 | 置信度`，并明确要求"推不出来就标待用户确认，不要编造"。这样即使某个 agent 挂了，也不影响已产出的稿子。
3. **必须自己复核 agent 的清单**。实测 agent 给出的建议有对有错——有的看着像"照着上下文编的"，其实完全正确（如 Jev / TypeSafe AI / Diogo Almeida 那三条）；有的确实是顺着语境拼凑。**不能凭印象定生死，必须先联网查证**。凡是有"高置信度"但依据只是"语境吻合"的，一律降级为待确认，**但必须先联网查证再决定是否采信**——判"幻觉"的前提是查过，不能凭印象（实测那三条建议 Jev / TypeSafe AI / Diogo Almeida 其实全对，被我误毙）。
4. **改之前先 dry-run**：把所有 `a → b` 替换逐条打印匹配位置和上下文，再执行。踩过的坑：
   - **子串污染**：`RAD → RAG` 会把 `ASRAD` 改成 `ASRAG`。给长词加占位符保护后再替换。
   - **替换顺序**：批量替换时，**新值不能被子串规则再次命中**。实测踩过：先做 `百分百含量 → 百分百 AI 含量`，再全局做 `含量 → AI 含量`，结果已改好的 11 处又变成 `AI AI 含量`。按"长串优先"排序，或先把所有待改串换成唯一占位符、最后统一还原。
   - **同段多义**：同一个 ASR 错词在不同段落可能指不同东西（"配套"一处指 Google 账号、一处指 GitHub），不能无脑全局替换。
5. **同一名称多写法单独处理**：同一个人或产品可能出现三五种写法（某产品被写成 劳力炮 / lovely pop / lonely pop / loading pop，甚至被 ASR 截成三段）。这类拎出来问用户，不要自己挑一个统一。
6. 交付时给一份**待核清单**（已改的 + 保留的），并把"改了但依据较弱"的单独标出来，方便用户抽查纠错。

### 第 7 步：交付 + 交代遗留

**在交付说明里列出"保留待核的可疑专有名词"清单**（ASR 把人名 / 模型名 / 产品名转错的那些），让用户拿术语表复核。这一步不能省——因为规则是保守保留，稿子里必然还留有可疑词。

## 交付后的答疑纪律（用户问"课上/录音里讲的是什么"）

**不要用自己的领域知识组织答案，必须先回原文检索。** 实测翻车：用户问"什么是数据、数据分哪些"，我按通用数据分类答了"结构化 / 半结构化 / 非结构化"三档，还把它当成课程内容写进了表格——但课上老师**只讲了两类**（非结构化、结构化），**"半结构化"这个词在全部文件里一次都没出现过**，是我从通用知识里夹带进去的。用户一句"有半结构化数据？"就把这个漏洞戳穿了。

- 答"课上讲了什么""老师怎么说的"这类问题，**第一步永远是 grep 原稿关键词**，把原话和段号调出来再组织答案。
- **严格区分三种信息，并在答案里标明**：① 老师原话（必须给段号）；② 我补充查证的（必须写明"这是我补的"）；③ 通用领域知识（必须写明"课上没讲"）。
- 用户拿课纲之外的术语来问时，先答"课上有 / 没有"，再决定要不要展开通用知识——**不要默认对方问的就是课上的口径**。
- **一个反向信号**：如果答得很顺、表格填得很满，但一段原文都没引用，大概率就是在拿自己的知识库糊弄。

## 踩过的坑

- **沙箱 overlay**：不带 `dangerouslyDisableSandbox: true` 的删除 / 移动只作用在 overlay 视图，验证结果会骗人（详见 macos-app-uninstall skill）。
- **子 agent 静默失败**：派发成功 ≠ 产出成功。第 4 步的逐块校验必须做。**实测块越小越稳**——200 段/块时多次出现某块不产出文件，改成 **115 段/块（3 块）后一次全成**。长稿优先拆小块，多派一路的成本远低于返工。
- **洗稿 agent 会洗得偏保守，压缩比就是信号**：正常水平 **0.76-0.85**，某次三块洗完是 **0.91**，复查发现第一版残留 **190 处**口语填充（`对吧`37 / 句尾`吧`45 / `呢`32 / `就是说`31 / `对不对`18 / 句首`然后`17 / `OK`1）。**压缩比明显高于历史值时必须补一轮残留扫描。** 这类词位置极规律，几条正则可批量清掉（实测一次清 79 处、语句全部通顺）：
  - `，对吧？` / `，是吧？` / `，对不对？` → `。`（换成句号，别删成空，否则句子失去句末标点）
  - `^然后\s*` → 删行首
  - `[，,]\s*OK\s*(?=[，,。？！]|$)` → `，`（**分隔符和词边界都不能省！** 实测用宽松版的 `[，,]?OK[，,]?` 把 `跟OKI合作` 改成了 `跟 ，I 合作`，毁掉一个疑似机构名。凡是以字母结尾的口语词，正则里必须加 `(?![A-Za-z])` 之类的右边界）
  - 替换后**必须扫异常标点组合**：`。。` `？？` `。，` `，。`（实测出现 1 处 `。，`，需修）
  - **替换后还要扫"标点后紧跟单个大写字母"**（`[，、。；]\s?[A-Z](?![A-Za-z])`）——这是正则吃掉专有名词前缀的典型残骸，一眼就能看出来。
  - 注意 `就是说` 是 `也就是说` 的子串，统计残留时会重复计数，别被数量吓到。
- **引号**：交付的中文稿里用中文引号「」或""，不要用英文直引号；但**代码和命令里必须用 ASCII 直引号**。
- **原稿被"追加更新"时，先做前缀比对再动手**：实测用户把下午的课**直接追加进上午那个文件**（88KB → 218KB）。一行一行比对后发现**前 692 行一字未改**，于是上午那 346 段直接复用已洗好的版本，只洗新增部分——省掉一半工作量，也避免了重洗引入的段错位。**如果不比对就整份重洗，纯属白干。**
  - **追加的部分行号规律可能和前半段相反**。实测 0924：上午段落在**偶数行**，下午追加进来的段落却在**奇数行**；两半的接缝处是**两个非空行直接相邻**（中间没有空行）。所以判据不能只测一次——要**分别验证前半段和后半段**，再按各自的规律算分块起始行。按老规矩硬算，分块会整体偏一段。
- **段数校验之外，还要做"顺序对齐校验"**：光比总段数不够。实测手工洗 110 段时，把原文两段合并成了一段（因为这两段首尾是同一句话的重复），总数直接从 786 掉到 785——**总数能抓到异常，但定位要靠对齐**。做法：对每一块用 `difflib.SequenceMatcher` 做贪心单调匹配，输出「未匹配到的原文段号」，一眼就能看出被吃掉/重复的是哪一段。
  - **更隐蔽的情况：同时"拆一段 + 并一段"，总数完全不变。** 实测手工洗 79 段时，把源文段 337 拆成两段、又把段 338 和 339 合并成一段，`497 = 497` 的校验一路绿灯，是**逐段相似度排序**把它揪出来的（被并的段比值 2.64、被拆的第一半比值 0.25）。所以：**压缩比异常（>1.2 或 <0.4）的段一定要逐段看原文对照**，这是唯一能发现"等量错位"的信号。
  - **手工洗稿比 agent 更容易犯"合并相邻段"的错**（人会觉得两段重复就顺手并了），所以手工洗的部分更要做这一步。手工洗完之后，**必须对这块单独跑一次顺序对齐校验**，不能只信自己数对了。
  - **二次清理脚本本身会"删段"和"留残渣"——这两类都是自己造的，必须复检**：
    - ⛔ **"清空就删"会造成段数少 1 + 整体错位一格**。原稿里存在只由标点/乱码构成的段（如 `**。`、`****。`）。若清理时先去掉句首标点、再写 `segs = [s for s in segs if s]`，那个空串就被删掉了：总数从 811 变 810，**而且从删掉的位置起，后续所有段整体错位一格**（output 的内容对上了下一段源文）。这种错**段数校验只能报"少 1"，定位要靠宽窗口对齐**。正确做法：清空则**回写原值**（`fixed.append(s2 if s2 else orig)`），保住段数。
    - ⛔ **删连词的规则会在标点处留残渣**。`(?:对吧|是吧|对不对)[，,]?` → `""` 把"，对不对？"变成"，？"（实测一次留 58 处）。**替换完必须再扫一遍标点组合**：`，？`、`，。`、`。，`、`，，`、`？，`，一并修掉。
    - 顺序建议：先修标点残渣 → 再处理句首标点 → 最后跑顺序对齐校验，别一步到位。
- **引用段号前必须机器校验——别把 Read 的"行号"当成"段号"**。实测翻车：交付给用户的整理稿里，**所有段号其实都是 Read 输出左侧的行号**。段落位于奇数行时两者差约一倍（`段号 = (行号 + 1) / 2`），用户拿这个号回原文会对到完全无关的地方。**这个错特别容易犯，因为 Read 左边那列数字看起来就像段号。**
  - 做法：交付前跑一遍机器校验——把稿子里引用的每个段号提取出来，回原稿取该段落，检查预期关键词是否命中。一段脚本就能抓出全篇错位（实测一次校验出 20 多处，全是行号）。
  - 根因是"从 Read 的输出来数段落"。更稳的习惯：**用脚本按空行切分原稿、打印 `[段N] 内容`**，直接拿真段号再引用，从源头避免。
  - ⚠️ **这条必须当成硬性收尾步骤，不是"最好做一下"。** 实测同一天的一份清单里连犯了 6 次（`妍妍` 720→296、`小乔` 776→326、`立体知识` 891→378、`蚂蚁 GLM` 302→362、`蜜雪冰城` 458/460→390/394、`飞猪→飞书` 标成"333 前后"实为 16/329）——**全是凭印象写段号**。凡是清单/汇总里出现 `段 N`，交付前一律过脚本：抽取 → 回稿取值 → 比对预期关键词。不通过不许交付。
  - **稿子做过"去杂音"后，还要额外做一次编号重算**：`新号 = 旧号 − 删前 ≤ 旧号的段数`，然后对新编号再跑一遍上一条校验。
- **缩写被 ASR 打散成常见词时，agent 会按字面意思理解，而不是往术语上还原**。实测两例：`V值` 被转成"位置"、`P值` 被转成"颜值"——洗稿 agent 于是把"一个 P 值下多个 V 值"写成了"一个颜色下面多个位置"，看着通顺、逻辑全无。**识别信号：句子里出现"读着顺但逻辑不通"的搭配。** 判据是往回找同一段/邻近段落里该术语的规范写法（前一段刚讲过"P 值是属性、V 值是属性值"，后面就不可能突然变成"颜色/位置"）。
  - 同类高危词：`QKV`/`QKAV`、`SFT`/`SMP`/`SMT`/`SMG`/`PST`、`RAG`/`RED`/`REG`、`MLP`/`MLB`/`ILP`、`LoRA`/`Laura`/`一条`/`牢牢`、`MCP`/`MCD`/`MCT`/`MCPE`/`SCP`、`tool`/`to`/`two`/`h two`/`库`、`API Key`/`APIK`/`AK`、`skill`/`CPU`/`SQL`（技能语境）、`TTS`/`TPS`/`PPS`、`markdown`/`马上语法`/`迈克尔语法`/`massachusetts`/`马克思`、`井号`/`顶号`/`鼎皓`、`星号`/`新字号`、`加粗`/`加速`（markdown 语境）、`系统提示词`/`系统支持`/`user prompt`/`system prompt`/`system front`/`master from`、`Dify`/`DB`/`DJ`、`博查`/`博茶`/`薄茶`、`飞书`/`飞猪`/`非洲`、`蜜雪冰城`/`秘籍名城`、`chunk`/`trunk`、`蚂蚁 GLM`/`aunt GRM`、`智谱`/`质谱`。
  - **一条通用判据**：这类错误几乎总是成串出现的——如果发现某一段里有一个词明显是 ASR 错，那段里通常还藏着 1-3 个同源错误（实测"但是在**山西**之前，其实我们是没有任何一个**生成时间**的"整句都是错的）。逐段核一个词时，顺手把该段其余可疑词一起扫掉。
- **临时文件**：分块产物写在 `/tmp/<task>/` 下，交付后清掉，不要留在用户目录里。
- **交付位置**：用户明确指定了输出目录时以用户指定为准，不要机械套用"产出平铺顶层"的默认约定。
- **别用"哪个更常见"判断缩写对错**：实测把 `NS难题`（Navier-Stokes 方程，千禧年七大难题之一）"修正"成了 `NP难题`（P vs NP，同一份名单里的另一个成员）——两个候选都能在语境里自圆其说，凭常见度下判断就是错的，这类必须问用户。审计清单里标为"低置信度"的建议，不要因为"看起来说得通"就提到高置信度去执行。
- **审计 agent 的"高置信度"要打折看**：它给的依据如果只有"语境吻合"，一律降级为待确认；如果把某条建议写进了交付清单的"依据明确"档，自己再验一遍。**但"我查不到"不等于"它不存在"**——实测 agent 给出的 `GEFGV→Jev`、`TYPEFC→TypeSafe AI`、`彪哥→Diogo Almeida` 被我以"疑似臆造"毙掉，事后 WebSearch 证实三条全对（Jev 是 TypeSafe AI 2026-09 发布的 System One Model，创始人 Diogo Almeida 是 OpenAI 前研究员、RLHF 应用先驱）。**对 agent 给出的具体人名 / 产品名 / 公司名，先 WebSearch 验证再定性**；把对的当错的删掉，比留着错的更糟。

## 洗稿后的复查（用户会问"哪里有问题、哪里改错了"）

交付前（或用户要求复盘时）跑这四类程序化筛查，再人工核异常项：

1. **压缩比异常**：`len(洗稿段)/len(原稿段)`，< 0.35 或 > 1.15 的都调出来看。
2. **数字丢失**：原稿含数字、洗稿对应段没有的（实测 50 段命中，绝大多数是 ASR 伪数字，逐类核完确认没有真实数字被误删）。
3. **英文术语差异**：分别统计「只在洗稿中出现」和「只在原稿中出现」的词，前者看有没有编造，后者看改得对不对。
4. **逐段相似度排序**：`difflib.SequenceMatcher(None, 原, 洗).ratio()`，取最低的 15 段。

**第 4 项最关键——它能抓到"段落错位"这种段数校验抓不到的错误。** 实测：我把原文段 544 结尾的一句引子挪到了段 545 开头（因为觉得两段接不上），总段数没变、格式也没问题，只有相似度排序把段 544 的 0.57 标出来了。

另外要主动向用户交代两类"不是错但需要知悉"的情况：

- **agent 的"推断性补全"**：洗稿 agent 会把 ASR 残缺的写法按上下文补成完整术语——实测 `model`→`Reward Model`、`air max`→`AiHubMix`、`chat polo`→`Chatflow`、`logo`→`LoRA`。方向通常对，但严格说是加了原文没有的词，**要单列一档让用户判断**，不能混进"术语修正"里冒充改错。
- **自己造成的错误**：复查报告里必须包含这一项，别只报 agent 的问题。

## 处理长稿时的文件安全（血泪教训）

处理几百 KB 的长稿往往持续数小时，这期间**原始文件可能被外部因素弄丢**（同步插件、用户在编辑器里误删）。实测踩过一次，恢复路径如下：

1. 先排查三条路：① vault 里有没有 git、且该文件是否被提交过；② 系统废纸篓 / vault 内 `.trash`；③ **Obsidian 的 IndexedDB blob**。
2. **最有效的是第三条**：Obsidian 核心插件"文件恢复"的快照存在
   `~/Library/Application Support/obsidian/IndexedDB/app_obsidian.md_0.indexeddb.blob/`
   内容是**未压缩的原始文件文本**，可以直接 `grep -a "某句原文" 该目录` 定位，完全不依赖文件名索引。用"字节数 + 原文独有写法"双重确认后 `cp` 回原位即可。
3. **快照会被 Obsidian 在运行时清理**——找到就立刻落地，别只在原地查看。
4. 结论：**动手处理长稿前，先给源文件做一份副本**（哪怕只是 `cp` 到 `/tmp`），比事后抢救省事得多。

## 用户约定（洗稿类任务）

1. **产出与源文件同目录**——用户明确指定过输出位置时以用户为准，不要机械套用"产出平铺顶层"的默认约定。
2. **读音相近、语境明确的专业术语直接替换，不必逐条等用户确认**；只有真正推不出答案的才列入待核清单。这条能省掉大量往返。
3. **一人多写法的人名 / 机构名**（同一位老师被写成三四种）要统一为一种，并在修正记录里列明原稿的所有写法，方便用户核对。
4. 交付时同时给一份**修正记录**：已改的按类别列清、仍待核的单列，用户核对后只需回一句就能定稿。
5. **产出按天归档**：不把文件散在目录里，而是在源文件所在目录下建一个以日期命名的小文件夹（形如 `产品经理 0921/`），当天所有文件平铺在里面，一天一个文件夹。

## 从洗稿稿提炼知识点 / 清单（下游产出）

用户会持续要求把稿子里的内容提炼成独立文件——知识清单、职责清单、某个概念的专题笔记、知识点地图等。这类工作有两条硬规矩：

1. **动手前先盘点既有产出。** 用户手上通常已经积累了好几份清单（硬知识清单、职责清单、各概念的知识点笔记），**必须先 Read 或 grep 一遍，看目标内容是否已被覆盖**。实测翻车：按主题切块列了一份 20 多个模块的"知识点地图"，用户回一句"这些基本都写过了"——核对后发现其中 6 大块早已写进既有文件。
   - 做法：清单类产出**同时给出"已覆盖（写在哪份文件）"和"缺口"两栏**，只对缺口动手，避免重复劳动。
2. **口径可能和字面不一致，先确认再产出。** 实测两次：用户说"硬知识"，实际要的是"岗位职责"；问"数据分哪些"，实际指的是"结构化 / 非结构化"这个维度。**遇到模糊词先问一句口径，比闷头产出后被退回省事。**

另外，产出文件里引用原文时**必须带段号**（段号 = 洗稿版段号），方便用户回原稿核对；自己补的领域知识要明确标【补】，与课堂内容分开——这是"半结构化"那次翻车后立的规矩。

**顺手质检**：每次因为某个主题回原文核对时，**顺手扫一遍该段其余可疑处**。实测过一轮完整洗稿后仍会残留 ASR 错字——某一句话里同时出现多个错字时（例："但是在**山西**之前，其实我们是没有任何一个**生成时间**的"），整句一起被漏掉。逐主题回查时顺手补，成本极低；等用户自己发现，成本就高了。

**输出形式：优先一张大表，不要多级大纲。** 用户对长列表容忍度低，连续两次要求缩短（"写少一点""不要列这么多，列个大表就行了"）。同一份内容改成一栏到底的表格（如 `环节 | 怎么做 | 出处段号`）后即可通过。所以这类"XX 讲了什么"的请求，**默认直接给表**，别先铺三层标题再分点。

**选题自检：优先"有人、有事、有画面"，不要"课程概念"。** 这条是硬翻车换来的——某次给的 7 个点（先发制人/后发制人、不可能三角、抓锚点、FDE、炫酷≠元素堆砌…）被用户一句否掉："这什么狗屁，找点好一点的，说人话。"

原因是这些全是**课堂内部黑话**：没上过课的人不认识、没有搜索需求、也读不出任何画面。发给读者的东西，术语就是墙。

发稿前用这四条筛：
1. 标题里有没有**具体的人 / 事 / 物 / 数字**？——"有同学做了个吵架消气的产品" ✅ ／"模型选型的不可能三角" ❌
2. 一个**没上过这门课的人**两秒内能不能看懂？
3. 有没有**画面或冲突**？（翻车、被冤枉、反常识、有人被骂、有人对着干）
4. 语言是不是**口语**？把"变量""框架""锚点""本质上是"换成"这世界上没有""他就废在这儿""我到现在也没想明白"。

**四条里只中一两条的就别发。** 课程的"方法论"适合进自己的笔记，不适合进小红书；能发的是课上的**人和事**。

**汇总不能凭印象写，要按关键词系统检索**。实测翻车：写"重点汇总"时漏掉了整整一块内容（数据从哪来、造数据四步、指令请求三原则等），直到用户追问"XX 讲了什么"才回原文发现。做法：动笔前把几个**大颗粒关键词**（如"数据""训练""流程""来源""步骤"）在稿里各检索一遍，按命中段号逐一确认有没有成块的内容被漏掉——比通读一遍更可靠，也更快。

## 素材的二次利用（对外发布 / 自媒体）

用户会拿这些稿子去做内容发布。开头必须先讲三条硬约束，再谈选题：

1. **学员 / 同学的真实姓名、公司、学历一律化名处理。** 开班课这类内容里常有几十位学员的自我介绍，含真名和原雇主。课堂录音 ≠ 可公开发布，引用前必须化名 + 抹掉公司名，截图一律打码。
2. **不要点名课程与老师。** 直接写出课程名/老师名，可能被判定为未披露的推广；引用老师原话时改写成"我课上听到一个说法"，不要做逐字引用卡片。
3. **收益类数字绝不进标题。** 稿里转述的往期薪资、涨薪幅度、就业率，单独截出来就是收益承诺——这是平台查得最严的一类。要么不写，要么放正文并注明"课程内部转述的往期数据，不代表任何人"。

选题的组织方式：**按内容支柱归类，不按日期平铺**。散点发内容平台无法识别账号标签。可用的归类法是「人设 / 认知 / 求职 / 实操」四类，其中人设类（连载日记）是唯一自带更新节奏、不用每次从零想选题的一类，适合当主线。

**成稿后先跑一遍合规初筛**，用 `check-social-content-compliance` 这个 skill 里的 `scripts/scan_text.py`，把标题+正文+话题拼成一份待检文本喂进去。实测 5 篇文案的结果是 **高风险 0 / 需修改 0 / 人工复核 9**，9 处**全是词表误报**——`第一` 的序数用法（第一版 / 第一条 / 第一天）占 4 处，另有 `业界`、`安全`、`解决`。
- 所以：**扫描器只负责定位证据，判断必须回到完整语境**。别被"人工复核 9"吓到，但也不能因此就不跑。
- 反过来也要守住：凡是**收益承诺、榜单排名、测试数据、限时活动、站外联系方式**，命中就是真问题，必须改写而不是换同义词。

**讲"安全 / 漏洞"类话题的尺度**：可以讲"我们被套出底层模型"这种防护复盘（真实、有教训、有共鸣），但**绝不能给可照抄的攻击话术**——给了就从"分享防护"变成"教人绕过防护"，性质完全不同。做法是把手法抽象成一句"用虚构身份包装违规请求"，**不写具体领域、不写可直接复制的句式**。这条要在交付时明确提醒用户别往下放。

**两个措辞惯性坑**：
1. 只要出现"给自己学生用""我们班"这类**隐含机构身份**的表述，就模糊成"给自己人试用"——它容易被判定为变相推广。
2. 效果类陈述用**主观体验**（"效果比之前稳不少"）而不是**结论式**（"输出质量确实稳了很多"），后者更接近效果承诺。

**涉及真实品牌的练习作品**（课堂作业常见形态：给某个现成 App 做落地页 / 重设计）：可以发，但必须做两件事——① **显式标注"个人练习作品，非官方"**，避免被判定为未披露的商业合作或冒充官方；② **只评价自己的作品，不评价那个品牌**（写"我给某游戏社区 App 做了一版落地页"，不要写"某 App 做得不好"）。品牌名是否点出可以放宽，但那两句标注不能省。配图用自己做的页面截图没问题，**不要用品牌的官方 logo 暗示授权**。

**默认写短版。** 用户明确要求过"少写点文字"。第一版按长文格式写了 5 篇（每篇正文 300-600 字），被要求改成短版——**正文控制在 150-200 字**，只留钩子 + 结论，删掉铺垫和解释性段落。用户点名要"500 字内"时可以放到 400 字上下，但**不要超过 500**。给短版时保留「封面文案 / 标题 / 正文 / 话题」四件套，正文用短行分点、可直接复制。经验性的东西宁可留在对话里说，不要塞进正文。
