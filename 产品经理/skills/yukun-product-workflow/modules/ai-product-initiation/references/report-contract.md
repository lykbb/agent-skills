# 报告职责、颗粒度与生成接口

## 八章职责

| 章节 | 必须表达的推导结果 | 常用呈现 |
|---|---|---|
| 00 一页纸结论 | 一句话业务逻辑；关键问题与证据；对应解决专题、主要任务、优先级及承接方 | 逻辑条、问题卡片、专题条目、关键数字；最后撰写 |
| 01 问题在哪 | 用户实际流程的障碍、规模和代价；证据支持的判断；成因假设及其他解释；相关竞品比较 | 关键数字、路径、实际漏斗或证据表、对照表、数据缺口说明 |
| 02 要做成什么样 | 一次完整使用的今天、目标体验及每一步怎样衡量；整体价值与结果指标 | 用户旅程四列对照、指标表、必要的用户分群、原型截图 |
| 03 取舍原则 | 基于本项目证据与约束的规则；为什么；怎样判断具体需求的去留和先后 | 编号原则，分别写理由与判断规则 |
| 04 具体做什么 | 专题 → 任务 → 需求；每条需求的承接、负载、价值、前置条件、状态和可选的 P0／P1／P2；范围外事项及理由 | 专题头、任务说明、需求表（可按优先级筛选）、角色及负载标签 |
| 05 版本节奏 | 每版或每阶段的专题交付、时间、依赖、容量、估算状态与资源不足的取舍 | 版本×专题矩阵、阶段卡、团队负载与条件说明 |
| 06 决策待办 | 尚未闭环的具体事项、影响、确认方、时间或触发条件；数据与容量缺口 | 决策待办表、缺口清单 |
| 07 附录 · 详细资料 | 正文判断的可追溯支撑；实际需要的详细资料与未纳入范围项 | 折叠证据、完整需求池、分工、评测和测算依据 |

市场、竞品、AI 适配、效果门槛、成本和兜底应按照与本项目判断的关系进入这些章节，不另起一套课件目录。用户点名要的章节（如痛点、需求分析、竞品、功能、原型）按下表落位，不另加第九章：

| 用户的说法 | 放进哪一章 |
|---|---|
| 痛点、用户问题、调研发现 | 01 问题在哪 |
| 竞品分析、替代方案 | 01 问题在哪（作为问题和差异方向的证据）；详细对照放 07 附录 |
| 需求分析、目标用户、使用场景 | 01 问题在哪 + 02 要做成什么样 |
| 原型、界面、交互流程 | 02 要做成什么样（`figures` 截图配说明）；逐条交互需求放 04 |
| 功能清单、需求池、优先级 | 04 具体做什么；后置理由放 03 或 07 |
| 排期、里程碑、版本计划 | 05 版本节奏 |
| 风险、待确认事项 | 06 决策待办，或放在受影响的需求和阶段旁 |

问题诊断不是竞品功能清单；目标状态不是孤立指标；取舍原则不是泛化检查清单；决策待办不是风险名词集合。

报告不足时应减少承诺、明确验证任务，并保留讨论稿状态。不要为了完整填满栏目而构造事实、团队、精确收益或时间。页面上的建议、目标和估算与实测值应清楚区分。

## 两份交付物

- `项目名称-立项与规划.html`：面向决策者的结论、证据和执行安排。默认自包含，离线可打开。
- `项目名称-工作底稿.md`：项目约定；已确认选择；证据索引（来源、时间、口径、可信状态）；假设及替代解释；未决项；验证任务（假设、方法、样本、判定、确认方、时间）；当前阶段与进入下一阶段的条件。

底稿记录的是本次项目，不回写通用 skill。已有文件未经授权不覆盖；使用新版本名或先取得具体覆盖授权。

## 生成接口

`scripts/render_report.py` 使用 Python 标准库，无需安装包。`--template` 选择视觉模板：`lime`（青柠，默认）或 `grid`（瑞士网格）；同一份 JSON 两套模板都能生成，内容和校验规则相同。选择方法见 [report-design.md](report-design.md)。输入为 JSON，默认从标准输入读取；`--input` 也可指定已经授权读取的文件。生成数据是当前项目的构建输入，不必作为第三份交付物保存。

```text
python3 /绝对路径/ai-product-initiation/scripts/render_report.py --template grid --html /项目目录/项目名称-立项与规划.html --workbook /项目目录/项目名称-工作底稿.md
```

为命令提供完整 JSON 标准输入，或使用 `--input /绝对路径/构建输入.json`。绝对路径替换为实际 skill 和项目目录，调用时不使用省略号。只写指定的两份新文件；现有输出路径会报错。

根对象字段：

| 字段 | 类型 | 内容 |
|---|---|---|
| `meta` | 对象 | `project`、`title`、`subtitle`、`owner`、`date`、`status`、`mode` 均为字符串；缺少责任人写待确认，不编人名。可选 `tagline`：一句话主张，网格模板放在报头大字处，缺省时用 `title` |
| `sections` | 数组 | 恰好八项；`id` 按顺序为 `s0`–`s7`，`intro` 为可选简短说明，`blocks` 为非空组件数组；章节标题由模板固定。可选 `headline`：本章结论句，网格模板用它作章节大标题，青柠模板显示在标题下方 |
| `workbook` | 字符串 | 完整 Markdown 底稿，记录上述项目状态与推导依据 |

文本自动转义，支持 `**重点**`、Markdown 链接和换行。HTML 标签显示为文本；不传原始 HTML、脚本或来自外部资料的执行代码。链接仅允许 HTTP、HTTPS 和页面内锚点。

组件选用：

| `type` | 字段 | 用途 |
|---|---|---|
| `text` | `text`，可选 `title` | 段落或小节说明 |
| `callout` | `label`、`text` | 一句话业务逻辑或关键说明 |
| `cards` | `items`，每项含 `badge`、`title`、`text` | 问题卡片，数量随项目变化 |
| `themes` | `items`，每项含 `label`、`title`、`priority`、`text`、`owner` | 结论页的专题、任务概览与主要承接 |
| `table` | `columns`、`rows`，可选 `title` | 通用证据、指标、决策和估算表；每行单元格数与列数一致 |
| `journey` | `rows`，每项含 `step`、`now`、`target`、`metric` | 完整目标体验四列对照；数据来源与未知状态写在 `metric` |
| `principles` | `items`，每项含 `title`、`reason`、`rule` | 取舍原则、理由与实际判断规则 |
| `requirements` | `themes`，结构见下文 | 专题、任务、具体需求的层级展开 |
| `roadmap` | `lanes` 字符串数组、`rows`，可选 `note` | 版本×专题矩阵；每行含 `phase`、`dates`、`cells`，单元格数与 `lanes` 一致 |
| `details` | `title`、`blocks` | 折叠附录，内部使用上述组件 |
| `funnel` | `rows`，每项含 `name`、`value`、`percent`，可选 `note` | 只用于口径已核对的真实漏斗；`percent` 为 0–100 的数字，不自动推断用户批次或流失原因 |
| `stats` | `items`，每项含 `value`、`label`，可选 `text`；可选 `title` | 关键数字，建议 2–5 个。`value` 以 1–48 的整数开头时画出同样数量的小方块，更大的数画成点阵；纯数字进入画面时滚动计数。只放有来源的数，口径写在 `text` |
| `figures` | `items`，每项含 `src`、`caption`，可选 `text`；可选 `title` | 原型或现状截图。`src` 必须是本机图片的绝对路径（png、jpg、gif、webp、svg，单张不超过 5 MB），生成时嵌入 HTML，离线可看；缩略图统一比例，点开看原图 |

`requirements.themes` 中每个专题含 `label`、`title`、`description`、`tasks`。每个任务含 `id`、`title`、`goal`、`rows`。每条具体需求含：

| 字段 | 含义 |
|---|---|
| `id` | 在当前报告内唯一的需求编号 |
| `name` | 需求名称 |
| `description` | 用户动作、能力或规则；标明对应问题、证据或目标体验步骤 |
| `owners` | 承接角色或确认方，尚未落实时明确待确认 |
| `load` | 主要工作负载；未经研发确认写初判／待估算 |
| `value` | 解决哪个问题、改善什么价值或指标 |
| `prerequisite` | 数据、标准、接口、法务、其他需求等前置条件；没有特殊条件也应说明 |
| `status` | 建议、已确认、待验证、待估算等实际状态 |
| `priority` | 可选，`P0`、`P1` 或 `P2`。P0 核心，立刻做；P1 重要，下个版本；P2 以后再加。同一个 `requirements` 组件里要么每条都填，要么都不填；填了以后表格多一列优先级，并出现按优先级筛选的按钮 |

优先级的含义固定为上面三档，不要另造「P0 = 本周」之类的口径；结论页 `themes` 的 `priority` 是自由文字，写到 P0／P1／P2 时会自动配色。

相同需求在多个版本、附录或讨论中引用其编号，不通过重复编号创建不同需求。生成工具检查重复编号、行宽、优先级是否齐全、图片路径和组件结构；它不能判断论证是否成立，内容质量仍按教练流程审查。

## 通用结构预览

`--demo` 仅生成不含业务案例的结构与方法预览，配套底稿说明它不是真实项目结论。它用于核对 UI、层级和工具，不可作为真实项目报告。

```text
python3 /绝对路径/ai-product-initiation/scripts/render_report.py --demo --html /项目目录/结构预览.html --workbook /项目目录/工作底稿示例.md
```

## 视觉与交互约束

两套模板共用同一套组件和八章顺序，长表格在窄屏横向滚动，正文仍按完整论证链排列。

- 青柠 `lime`：深色固定侧栏、纸色细网格底、蓝色与青柠色重点、深色逻辑条、圆角卡片。信息密、逐条可审，适合评审会和需要逐项核对的场合。
- 网格 `grid`：纸色底、黑字、一种红色强调；左侧目录带每章小节；报头大字主张、大号章节编号、描边英文背景字和十二栏辅助线；每章只用一到两个色块（逻辑条为红块，关键数字为浅色块）。留白大、叙事感强，适合展示、汇报和作品集。

两套模板的结构、字号和配色由模板固定，项目中不逐份改样式。需要新风格时先按 [report-design.md](report-design.md) 给用户看预览再定。

排版标准：

- 正文内容区在侧栏外的可用空间居中，设统一最大宽度与左右留白；窄屏按统一断点调整。
- 所有文字采用横排。表头、编号、优先级等短字段水平及垂直居中；长说明统一左对齐、正常换行。各表格使用一致的字号、行高、内边距与对齐规则。
- 表头保持一行，编号与短标签保持完整；不要插入逐字换行，或通过过窄的固定列宽形成一字一行。核算列宽时包括左右内边距，编号列至少能容纳表头与编号。
- 宽度不够时优先扩大列宽、优化长描述的占比或保留横向滚动；不靠缩小字体、截断信息或改成竖排凑版面。长段落的正常横向换行不视为竖排。
- 同类需求表复用相同列宽规则，给需求说明最多空间；不要为每张表分别指定互相冲突的局部样式。
- 桌面与窄屏均检查表头、编号和长表格；长表格在自身容器内滚动，不撑宽整个页面。项目排版微调不得覆盖这些通用规则。

动效只承担进入视野、悬停和导航反馈，节奏克制，遵循动效十二法则中与此场景有关的缓动、先后和视觉重点；遵守系统减少动态效果。无 JavaScript 时不隐藏正文。正文、代码、注释和底稿均不添加 emoji。
