# Yukun 产品开发工作流

复用包内三个模块，在独立业务目录推进一个项目：立项 → 可执行 PRD → 蓝图 → 实施 → MVP 验收。适合个人或小团队 AI 应用；默认本地交付，不承诺生产级或自动上云。

## 先定位，再进入当前阶段

1. 识别用户要讨论、规划、全流程开发还是续做，并沿用当前会话已给的实施范围。用户只要报告就停在报告；已要求做到 MVP 时继续承接，不因切模块重复询问是否开始。
2. 读取目标项目既有规则、资料、代码与状态。用户给定路径就是业务根目录，不能把本 Skill 或任一模块当作业务工作区；路径未给且无法可靠判断时只问这一项，不擅自在用户主目录建项目。
3. 先看 `docs/项目状态.md` 和当前需求；已有目录/文件约定时沿用并做索引，不为了套模板搬文件、重建工程或覆盖已确认内容。
4. 确认当前客户端能否读写文件、执行命令及验证界面。没有这些能力时可做讨论和方案，明确无法实施，不声称生成了文件或跑通 MVP。

同一项目默认只维护一份当前 PRD、一份状态索引。阶段、材料归属与冲突裁决先读 [流程契约](references/workflow-contract.md)。

## 按阶段只加载必要材料

| 当前任务 | 读取与动作 | 离开本阶段的依据 |
| --- | --- | --- |
| 想法与问题尚未清楚 | [立项模块](modules/ai-product-initiation/SKILL.md)，用真实资料区分事实、假设与未知；形成八章立项报告及工作底稿 | 核心用户、问题、目标体验与本版范围有确认；证据不足仍保留标签 |
| 有立项或明确需求 | [立项到 PRD](references/initiation-to-prd.md)，沿用需求 ID，补正常/异常行为、数据权限和可执行验收 | 本次入选需求可交给实施者；关键缺口已解决或获准按假设做原型 |
| 需要架构与技术取舍 | [蓝图模块](modules/agent-blueprint/SKILL.md) 与其 [整合引导](modules/agent-blueprint/使用引导.md) | 架构、接口、状态和失败路径能追溯到 PRD；只选必要组件 |
| 已有可实施方案 | [实施适配](references/execution-adapter.md)，按需读包内技术/前端手册；先完成一个真实核心切片再扩展 | 代码、测试与界面共同覆盖本版闭环，不以骨架或页面截图代替运行 |
| 准备交付 MVP | [MVP 验收](references/mvp-acceptance.md)，实际运行、检查结果与必要失败场景 | 仅对实测覆盖范围报告通过；缺 Key/授权的真实环节继续标待验证 |

已有资料足以回答的问题不再提问。每轮只问会改变目标、范围、成本、隐私或交付的关键项；常规实现选择用一个有理由的推荐，不把技术栈选择整包扔给初学者。

## 一次授权贯穿，新增风险单独确认

当前用户指令和目标项目规则优先，其次是本总入口/流程契约，再是模块适配与原手册。三个模块是阶段能力，不是各自重启一次项目。

用户确认假设不等于事实验证；方案确认不等于模型质量通过。额外模型调用/费用、安装、外部写入、公开发布与删除覆盖按用户规定确认。没有 Key 可用 mock 推进工程，但最终标记真实模型验收待完成。

## 验证与交付

包内 `scripts/check_project.py` 仅做只读文件预检，显式指定 `--project-root` 和 `--stage planning|mvp`；它固定报告 `runtime_validation=not_performed`、`mvp_accepted=false`。不能用它或蓝图静态扫描代替真实运行验收。

交付必要代码、启动 README、当前 PRD、蓝图和项目状态；立项阶段保留正式报告与底稿。不默认另存问答回执、检查快照、日志或阶段证据包。持续维护的状态记录当前阶段、已定决策、验证范围、阻塞和下一步。

总入口与三个模块的来源、依赖和使用方法见 [README](README.md)。
